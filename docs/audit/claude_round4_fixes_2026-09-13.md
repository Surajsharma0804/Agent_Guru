# Agent Guru - Round 4 Fixes Summary (2026-09-13)

Follow-up to `docs/audit/claude_round3_fixes_2026-09-13.md`, in response to "now move to the other fixes and all." This round wired the round-3 work (generalized browser control) into the live pipeline, eliminated a real duplicate-implementation problem, and - the most important find - fixed a genuinely fake ("placeholder") messaging feature that had been silently lying to users about message delivery.

## Why the messaging fix is the important one this round

Everything else in this round is real, but it's incremental - better tab reuse, one less duplicate table. The messaging fix is different in kind: it's a case where the agent was **actively telling the user something happened when it didn't**, on what is very likely one of the most common request types ("message my friend that I'm running late"). That's not a missing feature or an edge case - it's the exact "silent failure" and "fake completion" this project's engineering standard calls out by name. It was found by reading the actual implementation behind a tool that looked complete from its signature and docstring, not by anything the user reported - which is the kind of check the "treat every part of the repository as potentially containing bugs" standard is asking for.

## What's still honestly true about messaging after this fix

"Sent" now means "the target app is open with your message pre-filled, ready for one tap/press to actually go out" - on every platform, not just desktop. This isn't a shortcut I introduced; it's `MessagingController`'s own deliberate design (documented in its module docstring) to never auto-confirm a send to a contact that might have been resolved wrong. Agent Guru does not currently have a way to complete that last tap itself (e.g., a vision-driven click on WhatsApp's send button) - that would be a separate, larger capability (screen understanding + precise click automation) and isn't part of this fix. SMS genuinely cannot be sent from a desktop without a carrier gateway that isn't wired up; Slack's URL scheme genuinely cannot address a channel or carry message text. Those are now reported honestly instead of silently faked.

## Duplicate-implementation debt still open (not touched this round)

While tracing this, I found a fourth, smaller instance of the same pattern that I deliberately left alone this round: `orchestrator.py::_action_communication` (the *rule-based*, non-LLM fallback path for communication intents) has its own small inline WhatsApp/Telegram/email URL-building logic, separate from `MessagingController`. I did not merge it in, because the rule-based intent recognizer (`platform/intent_recognizer.py::_RuleEngine._try_communication`) only ever extracts a *contact* from the utterance, never message *content* - there is no message text available on that fallback path to send in the first place, so "just open the app for the user" is the honest, correct behavior there, not a bug. Fixing that properly would mean teaching the rule-based intent recognizer to also extract "saying ..." message content, which is a separate, scoped piece of work I'm flagging rather than doing speculatively.
