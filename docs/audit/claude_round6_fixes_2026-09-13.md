# Agent Guru — Round 6 Fixes Summary (2026-09-13)

Follow-up to `docs/audit/claude_round5_fixes_2026-09-13.md`, in response to "continue fixing with your best technical and technology and best sense and engineering." This round audited `platform/controllers/application_control.py` — the code path that opens, closes, and switches between applications, including the "never close protected/system-critical processes" safety guard.

## Files changed

| File | Change | Verification |
|---|---|---|
| `platform/controllers/application_control.py` | **The "never close protected/system-critical processes" guard could be bypassed with an ordinary friendly name — the exact phrasing a voice command would use.** `close_application()` only checked the caller's raw input string against a set of protected process names (`explorer.exe`, `winlogon.exe`, `csrss.exe`, `lsass.exe`, `services.exe`, `svchost.exe`, `system`, `smss.exe`, `wininit.exe`, plus `code.exe`/`kiro` for the IDE). That check catches someone passing the literal string `"explorer.exe"` — but real input uses friendly names, and `_find_process_by_name()` / `_PROCESS_NAME_ALIASES` resolve `"explorer"` straight to the real, running `explorer.exe` (the Windows shell) via the app's own alias table, without ever touching the guard. A completely ordinary command like **"close explorer"** would sail past the safety check and kill the desktop shell — the protection existed but didn't actually protect the case it was clearly written for. Fixed by re-checking the *actually-resolved* process identity right before termination, on both paths that can reach it: (1) `close_application()` now looks up the real process name for the resolved PID via a new `_get_process_name()` helper and refuses if that name is protected, and (2) `_taskkill_by_name()` — the fallback path used when psutil doesn't find a PID (common for UWP/Store apps) — now filters every resolved alias against the same protected-name set before ever invoking `taskkill`, and refuses outright if every alias for the requested app is protected. Both checks share one canonical `_PROTECTED_PROCESS_NAMES` class constant instead of each method (previously just one) keeping its own copy, so there's one list to maintain and no way for the two paths to drift apart. | Real, executed test (14 checks, all passing) against the actual `ApplicationController` class and its real guard/resolution logic — only the OS-specific platform integration (not even importable on this Linux sandbox) is stubbed, never the code under test. Confirms: the literal-name case still works as before; the friendly-name bypass (`close_application("explorer")` when psutil resolves it to the real PID) is now refused with no `terminate_process` call ever made; an ordinary non-protected app (`"notepad"`) still closes normally; the `_taskkill_by_name()` fallback path (psutil finds no PID) also refuses the same friendly name with no real `taskkill` process ever spawned, closing the second half of the bug that the `close_application()` fix alone didn't cover; and the fallback path's legitimate use case (a genuine non-protected UWP/Store app with no psutil match) still invokes `taskkill` and succeeds. |

## Note on scope

This was a security-focused close read of one controller, not a rewrite. The rest of `application_control.py` — application-path resolution (`_resolve_windows_application`, `_resolve_macos_application`, system/program directory search), window-identifier sanitization, and process listing — was reviewed alongside this fix and found to already defend correctly against path traversal (realpath + prefix containment checks, rejection of `..`/path separators in bare names) and injection (no `shell=True` anywhere in the file; every `subprocess` call uses an argv list). No changes were needed there.
