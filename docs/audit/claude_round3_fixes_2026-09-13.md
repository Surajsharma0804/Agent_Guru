## What "any website/application" means here, honestly

Real, general browser automation for *opening* a site and *searching* it now works without a dedicated API or per-site integration code — that covers "open Spotify," "search this on Chrome," "look this up," and similar requests for effectively any website. This does **not** mean arbitrary in-page task automation (filling out a specific form, completing a checkout flow, clicking through an unfamiliar site's specific UI) — that is a much larger, open-ended capability, and claiming "works on every website" for that would not be honest. What's built and verified is the "open it" and "search it" primitives; task-specific automation on top of them is a separate, larger effort not attempted here.

## Known limitation of this round's verification

This sandbox's outbound network proxy does not let headless Chromium reach real internet destinations (`net::ERR_CONNECTION_RESET` even though `curl` through the identical proxy succeeds) — isolated as a sandbox/proxy-tunneling issue specific to this environment, not a defect in the code, by running the exact same navigation/tab-reuse logic against a real local HTTP server instead (which passed in full, including the actual bug fix). The `search_and_open()`/`open_website()` paths against real google.com/youtube.com should be spot-checked on the user's actual desktop, which has direct internet access and does not go through this proxy.
