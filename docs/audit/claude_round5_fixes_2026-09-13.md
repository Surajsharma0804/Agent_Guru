# Agent Guru - Round 5 Fixes Summary (2026-09-13)

Follow-up to `docs/audit/claude_round4_fixes_2026-09-13.md`, in response to "go for the next round with your full potential." This round moved into a real security/reliability audit of `platform/os_controller.py` and its `FileOperationsController` - the code path that lets Agent Guru create, read, update, delete, copy, and move files on the user's machine, and the one that shuts down or restarts the PC.

## Files changed

| File | Change | Verification |
|---|---|---|
| `platform/controllers/file_operations.py` | **`read_file()` never wrote failed reads to the audit log**, unlike every sibling method (`create_file`/`update_file`/`delete_file`/`copy_file`/`move_file` all do). Its only exception handler was `except PermissionError: raise`, with a comment claiming this let callers "detect path traversal violations" - but the actual traversal check (`_validate_path()` → `security/path_utils.py::safe_path()`) raises `ValueError`, not `PermissionError`, so that handler never once caught a real traversal attempt; it only matched the unrelated real-OS-permission-denied case. The net effect: a path-traversal attempt - exactly the event a module whose own docstring promises "audit trail for all operations" exists to catch - went completely unrecorded. Now catches `ValueError`/`PermissionError`/`FileNotFoundError`, logs each to the audit trail with the real error detail, then re-raises (preserving the method's documented raise-don't-return contract). | Real, executed test: a genuine path-traversal attempt (`../../etc/passwd`) and a genuine file-not-found both now appear in the audit log with a real, specific error message (`"...resolves to ... which is outside the permitted base directory..."`), where before they were silently dropped; a normal successful read is still logged exactly as before. |
| `platform/os_controller.py` | **The file-operations sandbox silently defaulted to the process's working directory.** `FileOperationsController` was constructed without a `base_dir`, so its own fallback (`Path.cwd()`) applied - meaning the effective sandbox for every `create_file`/`read_file`/etc. call depended entirely on how Agent Guru happened to be launched (desktop shortcut, terminal, background service), not on anything meaningful. In practice this meant real user requests like "save this to my Desktop" would very plausibly be rejected as a path-traversal violation, because Desktop isn't under whatever directory the process started in. `OSController.__init__` now takes an optional `file_base_dir` and defaults to `Path.home()` when not given - a stable, predictable boundary that actually covers Desktop/Documents/Downloads on every platform, independent of launch method. | Real, executed test: a fresh `OSController()` with no argument now sandboxes to `Path.home()`, and the real `FileOperationsController` instance underneath it actually receives that `base_dir`; an explicit override still works; end-to-end through the full `OSController.create_file()` facade, a file under the sandbox root is created successfully and a traversal attempt is rejected without creating anything outside it. |
| `platform/os_controller.py` | **`reset_pc()`/`shutdown_pc()` used fire-and-forget `sudo` on macOS/Linux and unconditionally reported success.** `subprocess.Popen(["sudo", "shutdown", "-r", "now"])` (or `reboot`/`poweroff`) was launched detached, with no way to supply a password if `sudo` needed one - plain `sudo` with no cached credentials or NOPASSWD entry just blocks waiting on stdin. Agent Guru would tell the user "PC restarting now" while the command sat hung in the background having done nothing. Added `_try_run_power_command()`: runs the real command via `sudo -n` (non-interactive) so a missing-password case fails fast instead of hanging, waits briefly to distinguish "genuinely proceeding" (shutdown/reboot itself doesn't return until the machine goes down) from "failed immediately," and reports failure honestly with an actionable message (configure passwordless sudo, or do it manually) instead of a fabricated success. | Real, executed test against real subprocess behavior - not a mock of the method - using fake `sudo` executables placed on `PATH`: a working-NOPASSWD sudo reports success; a sudo that needs a password now fails fast and honestly instead of hanging while success was already claimed; a slow-but-genuinely-succeeding command (mimicking real `shutdown`) is still correctly treated as success rather than a false timeout failure; a truly nonexistent command reports failure cleanly. Also exercised against this sandbox's own *real* `sudo` binary (confirmed present via `which sudo`) - its `reboot` genuinely fails here (no systemd/D-Bus in a container), and that real failure is reported honestly rather than as a fake success, which is the fix's core guarantee holding under an environment I didn't construct myself. |
| `platform/os_controller.py` | **The most consequential finding this round: one bad controller import used to crash the entire `OSController`.** All eleven controller imports (`ApplicationController`, `FileOperationsController`, `KeyboardController`, `MouseController`, `MediaController`, `MessagingController`, `ScreenCaptureController`, `SystemSettingsController`, `TextInputController`, `WindowManager`, `HardwareMonitor`, `ProcessManager`) lived in one `try: ... except ImportError: logger.exception(...)` block. Every one of those classes is later constructed through `_safe_init()`, which clearly exists to isolate a single controller's failure from the rest - but the shared import block undid that entirely: if even *one* of the eleven modules failed to import (a missing optional dependency like `pyautogui`, a platform-only module on the wrong OS, a genuine bug anywhere in any one controller file), every class name from every module in that block was left unbound, `_init_controllers()` then hit a bare `NameError` on the very first `_safe_init(FileOperationsController, ...)` call, and that propagated straight out of `__init__()` uncaught - not the graceful "some controllers unavailable" degradation the log message implied, but total failure to construct `OSController` at all. Replaced with `_import_optional()`, which imports each module independently and returns `None` per class on failure - which `_safe_init()` already handles gracefully (`None(...)` raises `TypeError`, already caught there), so a broken/missing controller module now only disables the controller(s) it defines. | Real, executed test that reproduces the exact failure mode: constructing `OSController` in an environment where 9 of the 11 controller modules are genuinely missing (not mocked - real `ModuleNotFoundError`s from real missing files). Before this fix that would have crashed with `NameError` before `__init__` even finished; now it completes successfully, `FileOperationsController` and `MessagingController` (the two modules that *were* present) initialize and work correctly end-to-end (real `create_file()` calls succeed), and the nine missing ones cleanly degrade to `None`/unavailable exactly as `_safe_init()` was always designed to handle. |
