# Agent Guru - Round 7 Fixes Summary (2026-09-13)

Follow-up to `docs/audit/claude_round6_fixes_2026-09-13.md`, in response to "continue fixing with your best technical and technology and best sense and engineering." This round audited `platform/process_manager.py`, its call site in `platform/os_controller.py`, and `platform/controllers/window_management.py` - the lower-level process-management API (separate from `ApplicationController`, fixed in round 6) and the window-arrangement/virtual-desktop controller, neither of which had been closely read before.

## Files changed

| File | Change | Verification |
|---|---|---|
| `platform/os_controller.py` | **`list_processes()` has always returned an empty list, no matter how many processes were running.** It called `self._process_manager.get_process_list()` - a method `ProcessManager` has never defined; the real one is `list_processes()`. Every call raised `AttributeError`, silently caught by a broad `except Exception`, and turned into `[]`. This also fed `get_system_info()`'s `process_count`, which has therefore always reported 0. Fixed to call the real method name. | Real, executed test: a real `OSController` backed by a real (not mocked) `ProcessManager` against this sandbox's own actual running processes - `list_processes()` now returns real, non-empty data including the test's own PID, and `get_system_info()["process_count"]` reflects it. Before the fix this was unconditionally `[]` / `0`. |
| `platform/process_manager.py` | **`terminate_process()` had NO protected-process guard at all** - unlike `ApplicationController.close_application()` (fixed last round), this lower-level, directly-usable API would terminate any PID handed to it, including `explorer.exe`, `lsass.exe`, or (since this class is genuinely cross-platform via psutil, unlike the Windows-only `taskkill` fallback) `init`/`systemd`/`launchd` on macOS/Linux. Now resolves the real process name via psutil and refuses before ever calling `terminate()`/`kill()`; PID 1 is refused unconditionally as a second, name-independent layer. To avoid a second, independently-maintained copy of the same safety-critical list drifting from `application_control.py`'s (exactly the class of bug the project explicitly prohibits), both now import the set from a new shared module, `platform/protected_processes.py`. | Real, executed tests: `terminate_process(1)` is refused before any syscall; a real running child process is refused (via a monkeypatched resolver simulating a protected name) and confirmed **still running** afterward - proving no kill signal was ever sent; an ordinary real child process still terminates normally. |
| `platform/process_manager.py` | **`terminate_process()`'s own docstring promises `ProcessTerminationError` on failure, but that exception was never actually raised anywhere in the file.** `psutil.AccessDenied` (routine - trying to kill a process you don't own or lack admin/root for) and a repeat `psutil.TimeoutExpired` (force-kill itself not completing) both leaked out as raw, undocumented psutil exceptions, silently breaking the contract for any caller that (reasonably) only caught the documented exception types. | Real, executed test: a real `terminate()` call that raises `psutil.AccessDenied` is now wrapped and re-raised as the documented `ProcessTerminationError`, not leaked raw. |
| `platform/process_manager.py` | **`start_process()` opened the child's stdout/stderr/stdin as `PIPE`, but nothing anywhere in this class ever reads from them** - `start_process()` returns only a PID; there's no `communicate()`/output-reading method at all. An OS pipe has a small, fixed buffer (commonly 64KB); once a launched program writes more than that to stdout or stderr, the write blocks and the process hangs forever waiting for a reader that will never come - a classic, well-documented subprocess deadlock, and not a hypothetical one: any ordinarily chatty launched program can trigger it. Switched to `DEVNULL`, which matches what actually happens (output is discarded) instead of setting a trap. | Real, executed test: a real child process instructed to print 500KB to stdout (well over a typical 64KB pipe buffer) now finishes executing promptly; before this fix, with nothing draining a `PIPE`, this exact scenario is the textbook case that hangs indefinitely. |
| `platform/process_manager.py` | **`start_process()` only caught `FileNotFoundError`**, letting `PermissionError` (a non-executable target file - common) and other `OSError` subclasses leak out raw and undocumented, again breaking the method's own promised `ProcessStartError` contract. Widened to catch `OSError` generally (which includes `FileNotFoundError`) while preserving the specific underlying message. | Real, executed test: starting a genuinely nonexistent executable path now raises the documented `ProcessStartError` with a real, specific message, not a raw `FileNotFoundError`. |
| `platform/protected_processes.py` *(new)* | Single shared source of truth for the protected-process-name set, replacing what would otherwise be two independently-maintained copies (`application_control.py`'s existing one, and the new one `process_manager.py` needed). `application_control.py` now imports from it instead of keeping its own local constant - no behavior change, confirmed by re-running round 6's own test scenarios against the consolidated code. | Round 6's friendly-name-bypass regression scenarios re-run against the consolidated `application_control.py` and confirmed unchanged: `close_application("explorer")` still refused, ordinary apps still close normally. |
| `platform/controllers/window_management.py` | **AppleScript injection in `_snap_window_macos()`.** `window_identifier` - untrusted text that typically comes straight from a voice/text command, and which is itself attacker-influenceable even as a *real* window title (a browser tab's title is whatever the visited page set it to) - was f-string-interpolated directly into an AppleScript script with zero validation. AppleScript has a `do shell script` command capable of running arbitrary shell commands; a stray `"` in the identifier could break out of the `contains "..."` string literal and splice in attacker-controlled AppleScript that `osascript` would then actually execute. Fixed by validating through a new shared `platform/window_identifiers.py` module (the same deny-list approach `application_control.py` already used for its own, separate macOS window operations) before the script is ever built. | Real, executed test: a malicious identifier containing an AppleScript/shell breakout attempt is refused, and - critically - `osascript` is **never invoked at all** for it (verified via a captured `subprocess.run` call list), proving the injection is blocked before it reaches the OS boundary. A normal window title still works and is correctly embedded in the generated script. |
| `platform/controllers/window_management.py` | **`_get_screens_windows()` only caught `ImportError`**, unlike its macOS/Linux siblings which both catch broadly and fall back to a default screen. Any other pywin32-level failure (`EnumDisplayMonitors`/`GetMonitorInfo` can raise a `pywintypes` error in edge cases - disconnected monitors, driver issues, some remote-desktop sessions) propagated uncaught, crashing `get_screens()` and everything built on it (`snap_window()`, `tile_windows()`, `cascade_windows()`). It also returned an empty list unconditionally if monitor enumeration succeeded but found nothing, unlike its siblings' explicit fallback. Both now fall back consistently. | Real, executed tests using fake `win32api`/`win32con` modules injected via `sys.modules`: a generic (non-`ImportError`) failure while enumerating monitors now falls back to a usable default screen instead of crashing; an empty monitor enumeration also now falls back instead of returning `[]`. |
| `platform/controllers/window_management.py` | **`arrange_windows()`'s bare `next(s for s in screens if s.is_primary)`** raised an uncaught `StopIteration` - crashing `arrange_windows()`, and therefore `tile_windows()`/`cascade_windows()` - whenever no screen in the list is marked primary. Not a hypothetical case: `_get_screens_linux()` sets `is_primary` purely from whether the literal word `"primary"` appears in a given `xrandr` `connected` line, which is a real, ordinary X-config state that can leave no display marked primary. Now falls back to the first screen (safe, since `get_screens()` is guaranteed non-empty after the fix above). | Real, executed test: `arrange_windows()` called against a screen list with `is_primary=False` on every entry no longer raises, still returns success, and correctly falls back to the first screen. |

## Note on scope and what wasn't changed

`application_control.py`'s own, already-tested `_sanitize_window_identifier` was **not** rewired to import the new shared `window_identifiers.py` module in this pass - deliberately, to avoid touching an already-verified, already-committed file for a change that wasn't required to fix the vulnerability at hand. The two implementations are kept behaviorally equivalent and the consolidation is flagged as a clean, low-risk follow-up rather than done opportunistically here.

`create_virtual_desktop()`/`switch_virtual_desktop()`/`close_virtual_desktop()` (Windows/macOS) work by simulating a blind keyboard shortcut (e.g. Win+Ctrl+D) or a fixed AppleScript key sequence, then reporting success as long as the simulation call itself didn't raise - with no independent verification that a desktop was actually created/switched/closed. This is a real limitation, but not the same class of bug as round 4's fake messaging tools: these calls do perform a genuine OS action in the overwhelming majority of cases. Reliable verification would require Windows' undocumented/unstable `IVirtualDesktopManager` COM interfaces or equivalent private macOS APIs - a much larger, riskier undertaking than this round's scope justifies. Flagging honestly rather than attempting a brittle partial fix. Similarly, `_list_virtual_desktops_windows()`/`_list_virtual_desktops_macos()` return a hardcoded single-desktop placeholder, explicitly commented in the source as such - both platforms lack a simple public API for this; same reasoning applies.
