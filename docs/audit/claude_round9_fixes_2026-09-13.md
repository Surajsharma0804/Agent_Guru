## Fixes applied

| File | Change | Verification |
|---|---|---|
| `platform/controllers/system_settings.py` | Fixed 9 `logger.info()` calls with broken %-style format strings: 6 had a lone trailing `%` after `%s` (`"Set volume to %s%"` / `"Set brightness to %s%"` across the Windows/macOS/Linux backends), which Python's logging module raises `ValueError: incomplete format` on; 3 passed a plain string with no placeholder alongside an arg (`logger.info("Bluetooth", "enabled"/"disabled")`, `logger.info("Airplane mode", ...)`), which raises `TypeError: not all arguments converted during string formatting`. Every successful volume/brightness change and every Bluetooth/airplane-mode toggle on macOS/Linux was printing a full Python traceback to stderr via logging's `handleError()` instead of the intended info line. | Reproduced both exception types directly in Python before fixing (`"Set volume to %s%" % (75,)` → `ValueError`; `logger.info("Bluetooth", "enabled")` → `TypeError`, captured via a real `logging.Logger`/`StreamHandler`). Confirmed all 9 sites fixed (doubled the literal `%`, or added the missing `%s`) and format cleanly with real args. `py_compile` clean. |
| `platform/controllers/screen_capture.py` | **Most significant fix this round.** All 3 platform backends' `start_recording()` spawned `ffmpeg` with `stdout=subprocess.PIPE, stderr=subprocess.PIPE`, and nothing in the codebase ever reads from those pipes. ffmpeg writes a continuous stream of per-frame progress stats to stderr by default; once that output fills the OS pipe buffer (~64KB, reached within seconds of recording), ffmpeg blocks on `write()` and the recording silently deadlocks. Because ffmpeg can then no longer service stdin either, `stop_recording()`'s graceful `b"q"` keypress (in `stop_ffmpeg_process()`) never gets processed - so any recording running longer than a few seconds would hang, then get force-killed by the existing 5s timeout, producing a truncated/corrupted output file. This made the screen-recording feature effectively unusable for any real-world duration. Fixed by redirecting `stdout`/`stderr` to `subprocess.DEVNULL` (neither is ever consumed); `stdin` stays a pipe so the graceful stop signal keeps working. | Real, executed reproduction: a real child process that writes ~640KB to stderr (~10x a typical 64KB pipe buffer) then exits. With the old `PIPE`/unread behavior, `process.wait(timeout=3)` timed out (still blocked) in every run. With the fix (`DEVNULL`), the same child completed in ~0.03s. `py_compile` clean. |
| `platform/controllers/media_control.py` | Reviewed in full. No bugs found - every AppleScript/subprocess invocation uses fixed integer key codes or hardcoded literals, never user-controlled strings; no injection surface, no pipe/deadlock risk (uses blocking `subprocess.run()`, not long-lived `Popen` with unread pipes). Left unmodified. | N/A - no change made. |
| `platform/controllers/input_control.py` | Deferred in Round 8 as low-priority dead code (unreferenced by `OSController`); fixed now for completeness. (1) `click_at()`, `drag_to()`, `drag_relative()`, and `scroll()` now validate screen bounds consistently with `move_to()` (factored into a shared `_validate_bounds()` helper; `drag_relative()` computes the resulting absolute position from the current cursor position first). (2) `KeyboardController.press()`'s list-input branch no longer bypasses `press_key()`'s logging - `pyautogui.press()` already accepts `str \| list[str]`, so `press_key(keys)` handles both uniformly. (3) `KeyHoldContext`: `__enter__()` no longer leaves already-pressed keys stuck down if a later key in the list fails to press (Python never calls `__exit__()` if `__enter__()` raises) - it now releases whatever was already pressed, defensively, before re-raising; `__exit__()` now attempts every key's release independently so one failed `key_up()` can't abort releasing the rest. | Real executed test (14/14 checks) against a fake `pyautogui` module standing in only for the OS-level input driver - the actual `MouseController`/`KeyboardController`/`KeyHoldContext` code ran unmodified. Covered: bounds rejected/accepted for all 4 methods, `press()` list/str both still reach `pyautogui.press()`, a simulated `key_down("shift")` failure mid-hold releases the already-pressed `ctrl` (no stuck key), and a simulated `key_up("ctrl")` failure during release still lets `shift`/`alt` release normally. `py_compile` clean. |
